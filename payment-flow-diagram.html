Payment flow — idempotency key + transactional outbox

Two independent state machines, one HTTP request. The idempotency table guards against the request arriving twice; the outbox table guards against the "PaymentSucceeded" event never reaching anyone.

1 · Idempotency key — inbound request

The idem_key PRIMARY KEY does the locking — no explicit SELECT ... FOR UPDATE. Two requests racing to insert the same key: exactly one succeeds, the other reads back whatever state the winner (or a previous, now-dead attempt) left behind.

2 · Transactional outbox — outbound event

The outbox INSERT happens inside the same transaction as the idempotency-key UPDATE — so "payment completed" and "event queued to publish" are atomic with each other by construction, not by coordination. The poller is a completely separate process on its own clock; a broker outage just leaves rows PENDING for a bit longer.

3 · Full picture — one request, both tables

Read top to bottom: the HTTP thread only ever touches idempotency_keys (twice, in two separate commits) and, in passing, drops one row into outbox_events. Nothing about publishing the event is on the request's critical path — that's the whole point.
